## 2. 产品身份

### 2.1 定位
- **一句话**：首个**多用户、多智能体、实时协作空间**（multi-user, multi-agent, real-time collaboration space）。把上下文、文件、应用、任务连成一个实时共享工作区。
- **核心理念**：用户和多个 AI 代理（Claude Code、Codex、Canvas 等）在同一个「大脑」般的环境中协作，避免人在代理之间来回复制粘贴上下文。
- **明确边界**：**"Tutti 不是你编码代理的替代品，它是你代理周围的实时共享工作区。"** 开源版最适合「一人、多代理」；VM 版适合「一人多设备」或「多人各自带代理协作」。

### 2.2 目标用户
- 独立开发者、设计师、产品经理、内容创作者——任何厌倦了在代理/应用间切换、重复解释上下文的人。
- 不是以「跨工具持久循环状态协议」或「个人 loop 工作区」为主定位，而是以「人机 + 多代理实时协作」为主。

### 2.3 差异点声明
- 跨代理「Big @」引用：可从 Codex 里 @ Claude Code 的历史对话、文件、应用调用、任务。
- 「+」引用：引用本地文件或应用生成物，供任意代理直接消费。
- 人机共用应用中心：图像生成、UI/UX 设计、文档、PPT 等，用户和代理均可调用。
- 目标转任务 + 控制中心：自然语言目标自动拆解子任务并分配，统一视图管理所有代理对话、待审批操作、运行任务。

## 3. 架构总览

### 3.1 系统形态
- **Monorepo**：`apps/`、`packages/`、`services/tuttid`、`tools/`、`docs/`。
- 两种运行形态：
  - **Tutti（开源版）**：代理本地运行，工作状态保留在本地；跨多个代理共享上下文、应用、输出、任务与运行状态。
  - **Tutti · VM（Early Access）**：每个代理在用户自己机器上的托管本地 VM 中运行；"房间（Room）"在云端实时共享工作状态（讨论、运行、产出），实现跨设备、多用户协作。**房间是隔离边界，仅同房间内共享**。

### 3.2 运行时/技术栈
- **桌面端**：macOS（dmg）、Windows（exe）下载；含 `apps/`（`desktop-app` / `macos-app` 标签）。
- **包管理/构建**：`pnpm`（pnpm-workspace.yaml）、Changeset 版本管理、Husky git hooks。
- **语言/运行时**：Node.js（`.node-version`）；Go（`go.work`，推测 `services/tuttid` 为 Go 编写的后台守护进程）。
- **代码质量**：`oxfmt` / `oxlint`（Rust 系 JS/TS 工具链）。
- **代理集成**：Claude Code、Codex、Hermes、OpenClaw（DeepSeek）等，通过用户已有订阅连接。

### 3.3 协议/传输
- 实时共享工作区依赖云端 Room 同步（Tutti · VM）；开源版为本地共享。
- 无公开证据表明存在 LoopDesk 式持久跨工具状态协议（`LOOP-STATE.json`）或 MCP/ACP 适配器优先策略。

### 3.4 可观测性
- 控制中心：集中展示所有代理会话、审批等待、运行任务，一键处理。
- 代理互相可见工作进度，可自主避免/解决冲突，决定并行或顺序执行。
- 无公开证据表明具备 LoopDesk 式 run log、成本观测、L1/L2/L3 成熟度门禁或 maker/checker 拆分。

## 4. 核心能力

### 4.1 实时共享工作区
- **Big @**：在代理中引用过往对话、文件、应用调用、任务（甚至跨代理，如从 Codex @ Claude Code 的历史）。
- **「+」引用**：引用本地文件或应用生成物，供下一步直接使用，无需下载/上传。
- **任务编排与多项目**：跨供应商（Claude、Codex、Hermes 等）代理可见彼此工作，避免冲突，决定并行/串行。

### 4.2 人机共用应用中心
- 内置图像生成、UI/UX 设计、文档、PPT 等应用，用户和代理均可调用（如 Codex 调用设计应用获得类 Claude Design 能力）。
- 应用生态：可使用官方、社区或自建应用；应用运行在用户已有代理订阅上，不捆绑转售模型能力。

### 4.3 减少事务性工作
- **目标转任务**：描述目标自动拆解子任务并分配。
- **控制中心**：统一视图管理所有代理对话、待审批操作、运行任务。
- **GUI 界面**：无需命令行，开箱即用。

### 4.4 代理/编排
- 任务编排：代理互相可见进度，可自主避免/解决冲突，决定并行或顺序执行。
- 目标驱动：自然语言目标（如"建个网站"）拆为子任务，人工审核后分配给适配代理。
- 跨代理调用：在 Codex 中指挥 @ Claude Code 执行，或让一个代理调用设计应用赋能另一个代理。

## 5. 企业版 / 团队特性（重点）

> Tutti 无独立的"企业版"命名，团队能力主要体现在 **Tutti · VM** 与实时共享工作区中。

### 5.1 多用户实时协作（Tutti · VM）
- **群聊（Group chat）**：与他人及其代理协作（Work with others / others' agents）。
- **同时编辑（Simultaneous editing）**：多人/多代理并发编辑同一工作区。
- **代理借用（Agent borrowing）**：可借用队友的代理能力。
- **跨设备同步（Across devices）**：房间内工作状态跨设备实时共享。
- **无部署分享（No-deploy sharing）**：本地 localhost 直接在房间内预览，无需部署。
- **跨协作者 Big @**：引用队友的代理对话 / 文件 / 任务。
- **房间级权限隔离**：仅房间内创建的内容对受邀者可见，其余保持私有。

### 5.2 协作治理边界
- Room 是隔离边界，仅同房间内共享；房间创建需邀请码（Early Access），下载 VM / 加入他人房间不需要。
- 本质是"多人各自带代理协作"的拓扑，而非中心化多租户 SaaS。

> 战略含义：Tutti 已把"团队能力复用"产品化为**实时共享工作区 + 跨代理引用 + 代理借用 + 房间级隔离**，这恰好是 LoopDesk 后续"团队能力复用"方向的最直接参照形态（只是 Tutti 偏实时协作，LoopDesk 偏持久循环状态）。

## 6. 团队能力复用与 AI 资产管理（对标重点）

### 6.1 团队能力复用（Capability Reuse）
- **跨代理上下文复用**：Big @ 让一个代理直接消费另一个代理的历史对话/文件/任务，天然是"能力跨代理复用"。
- **代理借用**：队友的代理可被借用，能力在人际/代理际流动。
- **应用中心共享**：设计/文档/PPT 等能力以"应用"形式人机共用，且可官方/社区/自建，构成可复用的工具能力库。
- **目标→任务分发**：自然语言目标拆子任务并分配给适配代理，是轻量级的"任务级能力调度"。

### 6.2 AI 资产管理（AI Asset Management）
Tutti 把下列对象纳入统一工作区资产治理：
- **统一工作区资产**：所有应用输出（图片、设计稿、文档、PPT 等）保留在同一工作区，任意代理通过「+」引用并直接用于下一步，无需下载/上传。
- **应用生态资产**：官方/社区/自建应用即"能力资产"，运行在用户已有代理订阅上，不捆绑转售模型能力。
- **产出/中间产物资产**：AI 生成物（中间产物、最终交付物）在人机之间集中化、流式管理。

### 6.3 与 LoopDesk 后续方向的关联
> **LoopDesk 产品设计的后续规划：在个人循环工作区之上，新增"团队能力复用"与"配套的 AI 资产管理"功能。**

Tutti 已是该方向的**强现成参照**：
- 团队能力复用：Tutti 用"实时共享工作区 + 跨代理 Big @ + 代理借用 + 房间隔离"实现；LoopDesk 若从"单人跨工具"演进到"多人/多代理协作"，可直接借鉴其 Room/Big @ 交互范式。
- AI 资产治理：Tutti 把应用产出与应用本身作为统一工作区资产；LoopDesk 的 memory/skills/artifacts 可借其"资产集中化 + 直接引用"思路，但需补上 LoopDesk 更看重的持久化、可审计、可版本化。
- **关键差异**：Tutti 偏"实时协作/云房间"，LoopDesk 偏"本地优先持久循环状态"；两者在"团队能力复用 + AI 资产管理"目标上收敛，但底层范式不同（实时共享 vs 状态内核）。

## 8. 竞争分析

### 8.1 与"个人循环工作区"的相关性
- Tutti 是**协作范式的最强参照**，但不是 LoopDesk 当前个人-loop 定位的直接克隆。
- 作为参考更强的是：跨代理上下文复用（Big @）、人机共用应用中心、目标→任务分发、控制中心统一视图、房间级协作隔离。
- 作为参考更弱的是：持久跨工具状态协议、loop 工程方法论、显式成本/安全纪律、工具无关的跨 Claude Code/Codex/Codebuddy/Trae/Gemini 交接。

### 8.2 与"团队能力复用 + AI 资产管理"方向的相关性
- Tutti 已把团队能力复用产品化为实时共享工作区 + 跨代理引用 + 代理借用 + 房间隔离；这正是 LoopDesk 路线图要进入的战场。
- Tutti 的 AI 资产治理（应用产出与应用本身作为统一资产）是可借鉴范式，但 LoopDesk 应补上持久化/可审计/可版本化以区别于"实时协作"。

### 8.3 战略差异化（LoopDesk 应坚持）
- 不去做又一个实时协作工作区壳。
- 赢在：可移植跨工具循环状态、明确 adapter-first 集成、带 stop condition / maker-checker / 预算护栏的循环工程、轻量 CLI + 本地 Web UI。
- 但需为路线图"团队能力复用 + AI 资产管理"预留：能力（skills/artifacts/memory）的**可分发、可审计、可版本化、可配额**边界，并可借鉴 Tutti 的 Room/Big @ 交互范式。

## 9. 对 LoopDesk 的启示 / 路线图关联

- 把 Tutti 视为**团队能力复用（实时协作形态）**的首要对标：
  - 交互范式：Big @ 跨代理/跨人引用、代理借用、房间级隔离、控制中心统一视图。
  - 资产范式：应用产出与应用本身作为统一工作区资产，直接引用、无需搬运。
- 不建议把 LoopDesk 变成重实时协作/云房间运行时；保持轻量、可移植、local-first、adapter-first。
- 推荐监控主题：
  - Tutti · VM 定价模型（邀请码/个人 vs 团队）、是否下探到小团队/个人。
  - 是否新增持久跨工具状态导出或 adapter 策略（超出其自身代理集成）。
  - 应用生态（官方/社区/自建）是否开放为可复用能力市场，与 LoopDesk skills/artifacts 形成竞争。
  - 房间级权限/隔离是否演进为更细的团队治理能力。
