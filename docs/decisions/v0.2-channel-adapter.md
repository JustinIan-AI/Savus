# LoopDesk v0.2 — Channel Adapter Draft

> Status: draft for review
> Date: 2026-07-14
> Owner: product/engineering
> Decision boundary: keep LoopDesk local-first and workspace-first; channels are optional control/notification surfaces only.

## 1. Context

v0.1 proved the local loop workspace, `LOOP-STATE.json`, MCP-first integration, minimal local Web UI, and CLI workflow for an independent developer.

v0.2 should add one optional external surface: **IM as a lightweight remote control and notification channel for the local loop workspace**.

This draft is inspired by public patterns seen in `chenhg5/cc-connect`, but the LoopDesk adapter must not become an IM-first product. The local workspace remains the source of truth; IM is a control panel and delivery surface.

## 2. Goals and Non-Goals

### 2.1 Goals
- Let developers inspect loop status, approve actions, and issue a small set of workspace commands from DingTalk, Feishu/Lark, Slack, and WeCom.
- Deliver loop notifications back to IM when local runs finish, escalate, or need attention.
- Keep all durable state, execution, memory, skills, artifacts, and approvals in the local loop workspace.
- Preserve the existing public naming: `LoopDesk` / `loop_workspace` / `LOOP-STATE.json`.

### 2.2 Non-Goals
- Replace the local CLI and Web UI with IM-first workflows.
- Build a general-purpose multi-channel runtime, team chat suite, or cloud room service.
- Support unrestricted shell access, broad media generation, or marketplace skill discovery from IM.
- Support personal WeChat as a v0.2 platform.

## 3. Scope

### 3.1 In Scope for v0.2
- One shared **LoopDesk channel adapter layer** inside the gateway.
- Four platform adapters:
  - DingTalk
  - Feishu / Lark
  - Slack
  - WeCom
- Normalized inbound command set limited to loop inspection and control.
- Outbound notification types limited to status, approvals, cost alerts, errors, and compact run summaries.
- Permission checks, admin allowlists, audit logging, and disable-by-default behavior.

### 3.2 Out of Scope for v0.2
- Personal WeChat, QQ, Telegram, Discord, Matrix, and additional IM platforms.
- Rich media pipeline, voice reply, file/image send-back as primary flows.
- Team rooms, multi-user workspaces, shared admin consoles.
- Public cloud sync as the default storage path.

## 4. Product Positioning

LoopDesk v0.2 channel adapters are **optional bridges** between local loop workspace state and messaging apps.

The intended user experience is:
- the developer's computer still owns execution, memory, artifacts, and approvals;
- IM becomes a remote dashboard and action panel;
- all inbound IM actions are normalized into workspace commands;
- all outbound IM messages are derived from local workspace events.

This keeps LoopDesk distinct from channel-first bridges.

## 5. Architecture

### 5.1 Placement

Use the existing adapter plane as the home for channel bridges, but do not elevate channels to the primary product surface.

```
User Surface
  - CLI
  - Local Web UI
  - Terminal / IDE

Control Plane
  - Gateway
  - Gateway RPC
  - Auth / Approval
  - Config

Loop Plane
  - Loop Engine
  - Triage / Maker / Checker / Escalation
  - Run Log
  - Budget / Cost

State Plane
  - LOOP-STATE.json
  - memory / skills / artifacts / worktrees

Adapter Plane
  - MCP Adapter
  - ACP Adapter
  - Tool Adapters
  - Channel Adapters  <-- v0.2 addition

External Surface
  - DingTalk
  - Feishu / Lark
  - Slack
  - WeCom
```

### 5.2 Core Data Flow

```mermaid
sequenceDiagram
  participant User as Developer
  participant IM as IM Platform
  participant Adapter as Channel Adapter
  participant Gateway as Gateway RPC
  participant Loop as Loop Engine / Workspace
  participant State as LOOP-STATE.json
  participant Notify as Outbound Notifier

  IM->>Adapter: normalized inbound event
  Adapter->>Gateway: authenticated channel command
  Gateway->>Loop: validate + execute workspace action
  Loop->>State: update state, run log, approvals
  Loop-->>Gateway: result / approval required
  Gateway-->>Adapter: response or pending state
  Adapter-->>IM: concise reply

  Loop->>Notify: workspace event
  Notify->>Adapter: notification payload
  Adapter->>IM: formatted message
```

### 5.3 Adapter Responsibilities

Each platform adapter owns:
- transport lifecycle and reconnect behavior;
- inbound message normalization;
- outbound formatting for that platform;
- platform-specific auth validation.

The shared channel core owns:
- command parsing;
- permission enforcement;
- rate limiting;
- audit logging into loop workspace records;
- mapping commands to existing gateway RPC and workspace services.

## 6. Platform Strategy

### 6.1 Transport Preference
- Slack: prefer Socket Mode to avoid public URL exposure.
- Feishu/Lark: prefer WebSocket or long-connection mode; webhook mode is optional fallback.
- DingTalk: use Stream Mode.
- WeCom: require explicit public-URL review gate before any public callback/webhook mode is enabled.

### 6.2 DingTalk
- Use stream-mode inbound with card-capable outbound where available.
- Keep replies compact; do not rely on rich card interactions as the primary v0.2 approval flow.

### 6.3 Feishu / Lark
- Support webhook and websocket transports, with websocket as the preferred default.
- Reuse existing encrypt_key / verification_token handling and event dedupe.
- Outbound: text and limited markdown; do not rely on complex cards in v0.2.

### 6.4 Slack
- Prefer Socket Mode for v0.2.
- Outbound: text, limited card summary; avoid heavy interactive forms in v0.2.
- Preserve thread reply behavior when possible; fall back to direct channel reply otherwise.

### 6.5 WeCom
- Start with webhook mode behind an explicit review gate.
- Require operators to document tunnel, secret rotation, and exposure risk before enabling public callback.
- Keep outbound messages alert-style and compact.

### 6.6 Personal WeChat
- Do not include in v0.2 documentation or default adapter set.

## 7. Command Surface

### 7.1 Design Rule
Every channel command must be a thin alias for an existing safe workspace action. If the underlying workspace RPC does not already exist, the command is out of scope for v0.2.

### 7.2 Allowed Command Set

| Command | Purpose | Safety class |
| --- | --- | --- |
| `/help` | Show compact command list | read-only |
| `/status` | Show session/model summary | read-only |
| `/current` | Show current work and loop state | read-only |
| `/list` | List recent work/log entries | read-only |
| `/history` | Show recent chat history | read-only |
| `/memory` | Show memory status | read-only |
| `/skills` | List loaded skills | read-only |
| `/model` | Show or switch model where safe | read-only or write-gated |
| `/abort` | Abort current turn | write-gated |
| `/new` | Start new session or work item | write-gated |
| `/approve` | Approve pending action | write-gated |
| `/reject` | Reject pending action | write-gated |
| `/cancel` | Cancel in-flight work | write-gated |

Deferred commands:
- `/dir`, broad shell access, admin config changes, team room commands.

## 8. Security and Safety Model

### 8.1 Defaults
- Channel adapters are **disabled by default** after install or upgrade.
- No channel adapter is started unless the operator explicitly enables it in config.
- Public URLs and webhook endpoints are opt-in, not defaults.

### 8.2 Identity and Access
- Use admin sender allowlists to decide who can issue write commands from a channel.
- Use existing gateway auth/approval boundaries; do not invent a parallel security model.
- Treat unknown senders as viewers or deny write commands outright.

### 8.3 Permission Enforcement
- Read commands may execute for identified senders without elevated workspace approval, subject to channel availability.
- Write commands require:
  - enabled adapter;
  - sender in admin allowlist or operator-equivalent trust level;
  - passing kill-switch, denylist, and budget checks;
  - mapping to an existing safe workspace RPC.
- If any safety check fails, return a compact status message and log the audit record.

### 8.4 Audit and Observability
- Every channel command writes an audit record containing sender, channel, command, safety result, workspace action, and timestamp.
- Notification delivery results are logged with platform message IDs when available.
- Secrets are redacted in all logs and status payloads.

### 8.5 Rate Limiting and Abuse Prevention
- Apply per-channel and per-sender rate limiting for repeated bad commands.
- Retry outbound delivery with bounded backoff; stop retries when the adapter is disabled or shutdown is requested.
- Keep IM session non-blocking: never hold a platform session open while waiting for local loop state.

## 9. Message Design

### 9.1 Outbound Notification Types
- Status: short loop/session state summary.
- Approval request: pending action, requester, and `/approve` or `/reject` hint.
- Cost alert: compact budget or spend threshold warning.
- Error: short failure class and next-step hint.
- Run summary: condensed outcome for completed work.

### 9.2 Platform Format Rules
- Default format: compact plain text.
- Optional platform formatting: limited markdown or light card summary when the platform reliably supports it.
- Fallback rule: when formatting fails or size limits are exceeded, resend a shorter plain-text message instead of raising an unhandled exception.

## 10. Configuration Model

### 10.1 Principles
- Config stays in the gateway config model, not in IM-specific sidecars.
- All channel entries include explicit enable flag, agent binding, debounce window, and secret placeholders.
- Public-webhook mode requires explicit operator review documentation.

### 10.2 Example Concepts

### 10.3 Secret Handling
- Secret fields are omitted from docs, UI status, and logs.
- Operators store secrets through the gateway config mechanism.
- Channel status shows connectivity and health, never raw credentials.

## 11. Implementation Plan

### Phase 1: Foundation + Two Platforms
- Shared channel adapter core and command parser.
- Slack Socket Mode.
- Feishu WebSocket / long-connection mode.
- Read-only commands and status notifications.
- Disabled by default; opt-in via config.

### Phase 2: Expand Platforms and Write Commands
- DingTalk.
- WeCom with explicit public-URL review gate.
- Write commands: `/new`, `/switch`, `/approve`, `/reject`, `/cancel`.
- Approval request notifications.

### Phase 3: Hardening
- Cost alert notifications.
- Rate limiting, abuse prevention, retry backoff.
- Error escalation templates per platform.
- Local Web UI channel status page.

## 12. Validation Criteria

### v0.2 Channel Adapter Exit Criteria
- A developer can enable one channel and issue `/current` from that IM without opening local Web UI.
- A developer can receive approval request and finish it with `/approve` or `/reject`.
- All channel actions are recorded in local run log / approvals / state records.
- Disabling a channel leaves local loop workspace behavior unchanged.
- No channel adapter exposes unrestricted shell, legacy chat surfaces, or team-room semantics as v0.2 public features.

## 13. Rollback and Safety

- Each platform adapter can be disabled independently.
- Disabling adapters must not delete or alter existing `LOOP-STATE.json`, memory, skills, artifacts, or worktrees.
- If a platform changes API behavior or account-risk posture, operators can disable that adapter without removing local workspace data.
- Rollback procedure:
  1. set platform `enabled = false`
  2. restart gateway
  3. verify local workspace behavior remains green

## 14. Open Questions

- Should v0.2 support only one enabled channel at a time, or multi-channel simultaneously? ✅ 已确认：允许同时启用多个 channel。
- Do we allow channel-driven `/model` and `/dir` in v0.2, or defer to v0.3? ✅ 已确认：纳入 v0.2。
- What is the exact Feishu and DingTalk message-size/card limit policy for v0.2? ✅ 已确认：默认只发 compact text，card 延后到 v0.3。
- Should WeCom require mandatory tunnel review before any public webhook can be enabled? ✅ 已确认：不强制 mandatory tunnel review，改为推荐 review。
- Do we need a dedicated `docs/channels.md` refresh for v0.2, or keep channel docs minimal/internal? ⏳ 待补充：保持 channel docs minimal/internal，但需确认 operator docs 范围。
- IM 扩大平台集合前，operator controls 如何定义？✅ 已确认：先只开放 approved set：DingTalk、Feishu/Lark、Slack、WeCom；其余平台延后，并通过 allowlist + disable-by-default + audit log 控制。

## 15. Decision

Approve this draft as the v0.2 channel adapter direction with the following constraint:

> LoopDesk v0.2 will add optional IM adapters for DingTalk, Feishu/Lark, Slack, and WeCom only when they can be implemented as lightweight control and notification surfaces on top of the existing local loop workspace. IM breadth is not a v0.2 success criterion; local-first loop continuity remains the primary product promise.
