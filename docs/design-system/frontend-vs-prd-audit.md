## 0. 结论摘要

1. 专家 4 项质疑**逐条成立**，但**归因需要修正**。实现本身是画布的 1:1 忠实还原（2026-09-12 复核：8 屏像素差异 2–5% 全部来自文字抗锯齿，腐蚀后**结构差异块 = 0**）。因此这些偏差不是"实现写错"，而是**画布与 PRD §9.11 的规范冲突被实现忠实继承**。
2. 覆盖率结论方向正确，**但口径必须区分**：按"PRD 能力在实现中可用"计，首次核对 **13 / 12 / 15**、**二次复核 17 / 10 / 13**（完整 / 部分 / 缺失）；按"设计稿视觉呈现有无"计则为 **17 / 9 / 14**（既有偏差清单**明细**口径——其 §1 汇总行 16 / 10 / 14 为笔误，已在本次一并修正）。
3. 除专家所列 4 项外，核对中另发现 **5 处实现层问题**（§6）。同步落地后：第 3 项（控制中心）经**勘误**（画布确有该导航项），第 5 项（交互层）由 13 处增至 **22 处**；但"点任务卡无响应 / 右栏关闭键死控件 / 项目切换器不可切换"三项仍在，**C5 任务详情仍不可达**。

## 4. 专家质疑逐条核对

### ① 主对象错位 —— 会话取代任务（Chat Shell）

**判定：成立**（且比"命名偏差"更重：是主对象被替换，不是措辞问题）

| 位置 | 实现 | 证据 |
| --- | --- | --- |
| 左栏主 CTA | `新建会话`（emerald 满宽）→ 打开会话抽屉 | `LeftRail.tsx:114-131` → `App.tsx:56,71` |
| 会话抽屉 | 标题「会话」+ 5 条会话行 | `SessionDrawer.tsx:50,106-169` |
| 中栏底部 | `ConversationDock` 常驻 **4 屏** | `TaskBoard.tsx:373`、`TeamAssets.tsx:296`、`ControlCenter.tsx:60`、`SettingsShell.tsx:131` |
| 数据层 | `SESSIONS` 与 `TASKS` 双对象并存，界面主位给会话 | `data.ts:36-56` vs `data.ts:248-254` |

PRD 对应项：§9.11.2「顶部：项目名 · 搜索 · **+ 新建任务**」；§9.11.3 L3「**新建任务**：列表顶部入口」；§9.11.1「术语分层：一级界面只说人话（任务 / 看板 / 对话 / 变更 / 成本 / 审批）」。

**归因：继承自画布**（画布 8 帧即以"会话"为主对象）。

### ② 看板第三列语义分歧 —— 评审中 ⇄ 待审批

**判定：成立，且实现内自相矛盾**

- `data.ts:32` → `{ id: 'review', title: '评审中', count: 2 }`，类型 `TaskColumnId` 已固化为 `'review'`（`data.ts:8`）。
- 同列两张卡（`ACME-196` / `ACME-188`）`state: 'gate'`，渲染文案为**「等待 operator 审批」**（`data.ts:41-42, 58`）。
- 即：**列标题写"评审"，卡内文案写"operator 审批"**，同一屏内两套语义。
- PRD §9.11.4 C1 与设计规格 §5.1 均为 **待审批**（"等待人工决策 · 审批队列 / escalation"）。
- **复核前快照**：以上是画布修订 v2 之前的状态。第二次复核后，PRD §9.11 与设计规格均已改写为 **评审中**（列）+ **审批门**（右栏区块），见 §10。

**归因：继承自画布，但矛盾在实现层被放大**（类型固化 + 文案未对齐）。

### ③ 缺 C4 新建任务面板（模板选择）

**判定：成立**

- `overlays/Modals.tsx` 仅导出 `AddAgentModal` / `AddConnectorModal`，**无模板选择面板**。
- 全仓检索 `issue-fix` / `pr-commit` / `auto-research`：仅作为资产卡名（`data.ts:121-123`）与分支名（`data.ts:37-44`）出现，**未构成可选能力**。
- PRD §9.11.4 C4（P0）、设计规格 §5.4 已给出面板线框（归属项目 / 选择模板 / 描述 / 取消 + 开始任务）。

**归因：实现缺口（画布同样未定义此区块）**。

### ④ 缺 R2 六阶段 Stepper；Goal / Gate / RunLog 抬到顶层

**判定：成立**

- `TaskBoard.tsx:210-345` 右栏七段**全平铺、无折叠**：`Goal · 目标` / `Handoff 上下文包` / `Agent 执行` / `审批门 · operator gate` / `Run Log` / `成本 / 配额`。**无 stepper**（仅两条扁平进度条）。
- 右栏标题为「任务检视器」（`TaskBoard.tsx:160`），PRD 称"上下文面板"。
- 右栏**无折叠能力**：`:162` 关闭图标仅有 `cursor:pointer`，**无 `onClick`**；违反设计规格 §7「右栏可整体折叠」。
- PRD §9.11.8 明确把 **Goal / Gate / Handoff / Validation Receipt 归为"三级（按需展开 / 设置）"**；§9.11.5 R2 要求六阶段 stepper（默认折叠为四项）。

**归因：继承自画布**。

## 7. 需要先裁决的治理问题

**画布 vs PRD 谁是准？**

- `AGENTS.md` §1.1 规则 3 声明 Ardot `724693301521075` 为"**前端事实源唯一**"；
- 但该画布在**主对象（会话 vs 任务）**、**第三列语义（评审中 vs 待审批）**、**右栏术语层级**三处与 PRD §9.11 直接冲突；
- 结论：**在裁决"谁为准"之前，P0 的 1–4 项无法开工** —— 改实现就偏离事实源，不改就偏离 PRD。
- **后续（2026-09-14）**：P0 第 1–4 项已按"先修画布、后改实现"完成裁决与落地，§10.2 记录结果。

**建议裁决顺序：先修画布、后改实现。** ✅ **该顺序已被采纳并执行完毕（2026-09-14）** —— 画布修订 v2 先落地，`frontend/` 随后同步；逐项结果见 §10。

1. 冻结主对象（建议以 PRD 的 **Task** 为准，画布侧改文案与 CTA）；
2. 统一第三列语义；
3. 画布补 **C4 新建任务面板** 与 **R2 六阶段 Stepper** 两个区块；
4. 画布定稿后再视为事实源继续实现，避免实现停在"两边都不对"的中间态。

**另注（引用陷阱）**：PRD §9.11 表格的"状态"列图例（`loopdesk-prd-v2.0.zh.md:18-22`）为 `✅ 已实现 / 🔶 已实现待验收 / 🆕 本次完整版新增`，指的是**产品能力状态**，**不是前端覆盖度**。引用该表时勿与"前端覆盖率"混用。

### 11.5 看板右栏（`2:171`）改为**三段生成模型**

此前的右栏是**写死的一版文案**，与"所选卡片"无关。本轮把它切成三段可复算的区块，并补上「交付物清单 + 超链接」；三段之外只剩尾部「成本 / 配额」。

#### 11.5.1 交互约定：单击 = 选中，右栏跟随

| 动作 | 结果 |
| --- | --- |
| 单击卡片 | **选中**该卡（高亮），右栏 `Inspector` 按该卡重新生成；**不跳转** |
| 单击右栏顶部「查看详情 →」 | 进入第 10 屏**任务详情**（该卡） |
| 单击交付物清单里的**内链** | 进入详情页并**滚动锚定**到对应区块 |
| 单击交付物清单里的**外链** | 新标签打开真实形态 URL（`target=_blank`） |

> `App.tsx`：`selectedId`（默认 `DEFAULT_TASK_ID = ACME-201`，故首屏右栏与画布逐字一致）与 `detail: {id, anchor?}` 是**两个独立状态**——选中不等于进详情。

#### 11.5.2 三段的分工与生成依据

画布在每个分组标题右侧标注了生成依据（与 `pr_contract` / `run_log` 同一种"标注语言"），实现侧由 `INSPECTOR_GROUP_RULES` 提供同一份字符串：

| 段 | 分组标题 | 生成依据（画布标注） | 实现取值 |
| --- | --- | --- | --- |
| ① | 任务状态 | `card.state` | 状态芯片 + 六阶段 + 处置·路由/验证，**全部**由 `card.state` 三档推导 |
| ② | 详情 | `card.detail` | Goal / Handoff / Exec / Gate / RunLog，由卡片字段 + `state` 推导 |
| ③ | 交付物清单 | `card.state · 3 项` | `deliverablesFor(card)` —— 清单**由 state 决定**，卡片不携带清单 |

**统一入口**：`inspectorView(id)`（`data.ts`）——给一个任务 id，换回 `{card, status, detail, deliverables, cost}`。`TaskBoard` 只消费它，不内联任何文案常量。

#### 11.5.3 ① 任务状态

- 状态芯片：`INSPECTOR_STATUS_TEXT[state]` → `handoff` / `评审中` / `已交付`（22px 芯片只放得下一个短词，故不复用卡片那句长文案）；色沿用 `CARD_STATE_COLOR`。
- 六阶段进度：`STAGE_BY_STATE[state]`（分诊 / 制作 / 检查 / 升级 / 日志 / 停止）—— `handoff` 停在"检查"、`gate` 停在"升级"、`delivered` 全 ✓；摘要句同表。
- 处置·路由 / 验证：路由三选一的**选中项**由 `ROUTE_BY_STATE[state]` 决定（`handoff`/`gate` → 备修复 · fix_pr，`delivered` → 仅记录）；运行条 `DISPOSITION_RUN[state]`。
- **两段式验证铁律**：`✗ 复现失败` 与 `✓ 修复通过` **必须成对渲染**（`DISPOSITION_VERIFY`）——只看结果无法判断修复是否真的生效。

#### 11.5.4 ② 详情

| 子块 | 生成依据 |
| --- | --- |
| Goal 标题 + 摘要 | 卡片 `goal` + `GOAL_SUMMARY_BY_STATE[state]`（待确认条数随 state 变） |
| Handoff 五段 | 目标 = 卡片 `goalBrief`；决策 = `DECISION_BY_STATE`；证据 = 卡片 `evidence`；待办 = `TODO_BY_STATE`；交接 = `转交 {card.agent} · {card.branch}` |
| Exec 进度 | `card.agent` + `EXEC_BY_STATE`（运行中 3/5 → 已暂停 5/5 → 已完成 5/5） |
| Gate | `GATE_BY_STATE`：`delivered` 时待处理数归 0、文案转「已放行」、tone 由 amber 转 ts |
| RunLog | `RUNLOG_BY_STATE`，其中的 `%EVIDENCE%` / `%AGENT%` 占位符由 `fill()` 用卡片字段回填 |

#### 11.5.5 ③ 交付物清单 + 超链接（新增）

清单构成**由 task 的状态决定**——在跑的任务只交出"半成品"，待审的交出评审包，已交付的交出凭据与记录。卡片本身不携带清单，避免同一任务两处维护。

| state | 行（节点 `37:17` / `37:21` / `37:25`） | 链接 |
| --- | --- | --- |
| `handoff` | `feat/handoff-ctx` | **外链** → `github.com/acme-platform/handoff-ctx` |
